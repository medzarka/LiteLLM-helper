App Objectives

LiteLLM Helper is designed to be the ultimate Control Plane for the LiteLLM AI Gateway.

Its primary objective is to simplify and automate the complex configuration of LiteLLM proxies. Instead of manually editing large YAML files, this app provides a structured UI to manage providers, API keys, routing rules, load balancing, and model capabilities. It ensures the AI stack remains robust, scalable, and easy to maintain by dynamically generating and syncing configurations to the live gateway.

Interface Roles
Interface Role & Purpose
Providers Define the AI service providers (e.g., OpenAI, Groq, OpenRouter) and set their base URLs.
API Keys Store and manage multiple API keys per provider. Enable or disable keys instantly.
Models Configure specific models, their context windows, capabilities (Function Calling), rate limits, and custom tags/skills.
Aggregated Models Create shared aliases (e.g., `smart-model`) that route traffic across multiple underlying provider models for load balancing and redundancy.
Key Rotation Configure how traffic is distributed across the API keys (e.g., Round Robin, Random) to optimize rate limits.
Fallbacks Define failover chains so that if a primary model fails, the request is automatically routed to a backup model.
Export Config Generate the final `config.yaml` file, sync it live to the LiteLLM Docker container, and manage Configuration Versions (snapshots) to roll back safely.
Hermes Agents Map task-specific virtual models (e.g., `hermes-vision`, `hermes-mcp`) directly to the backend models. Easily assign Fallback Models to ensure Hermes tasks never fail if the primary model rate-limits. Seamlessly swap Hermes models without editing its internal config.
Model Health Ping and verify the availability and latency of the models in real-time.
Useful Tips & Hints
Aggregated Models vs Fallbacks

Use Aggregated Models when it is desired to load-balance across multiple providers simultaneously (e.g., routing `llama3` traffic to both Groq and OpenRouter to share the load). Use Fallbacks when a primary model is strictly preferred, and a secondary is only used if the primary fails.

Managing Free-Tier Keys

When relying on free-tier APIs with strict limits:

  • Use Fallback Models aggressively to route to an alternate free tier provider (e.g., OpenRouter) when the primary (e.g., Groq) fails.
  • Avoid Aggregating rate-limited APIs with unlimited APIs, as load balancing is blind to current quota usage.
  • Keep retries low (1-2) to avoid retry storms that consume the remaining quotas.
No Restart Required

There is no need to restart LiteLLM when changes are made. Navigate to the Export Config page and click "Sync to Live LiteLLM". As long as the LiteLLM container is running with --reload, it will hot-reload the changes instantly!
